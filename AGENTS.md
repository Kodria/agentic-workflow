# AGENTS.md — Guía de mantenimiento de AWM

Esta es la guía de mantenimiento de este repo (el CLI de AWM) — no la función del propio CLI que genera un `AGENTS.md` para *otros* proyectos (ver `cli/src/core/context/strategies/`, `cli/src/core/renderers/`). Cada entrada de abajo es un patrón de ingeniería confirmado contra el código real de este repo, curado con la misma disciplina merge-and-prune que aplica `harness-retro` sobre cualquier proyecto: fusionar lecciones nuevas en las secciones existentes, podar lo que ya no aplica, nunca apilar un log crudo por encima. La procedencia detallada de cada hallazgo (qué release, qué fecha, qué commit) vive en el historial de git y en `docs/plans/` — este documento guarda la lección generalizable y accionable, no el diario de la sesión que la produjo. Todo agente que trabaje en este repo debe leerlo antes de tocar código.

---

## Patrones de testing

- **platform-property-assumed-universal:** el modo de falla mas caro de este repo *(×5 en un solo ciclo: 4 los encontro la CI de Windows, 1 la de macOS, ninguno el desarrollo en Linux)*. Un test que **simula** una plataforma (`Object.defineProperty(process,'platform',…)`) mientras corre sobre el filesystem real de otra no verifica nada en ninguna de las dos: cambia lo que hace el CODIGO, no lo que hace el DISCO. Clases confirmadas: el bit de ejecucion (Windows no lo tiene, `chmod 0o644` no lo quita), el separador de ruta, comparar un prefijo de home antes de normalizar separadores, el fin de linea (un checkout de Windows entrega CRLF), y `/var` → `/private/var` en macOS. **La contramedida no es "correr en mas plataformas"** — eso los encuentra tarde y caro. Es exportar la unidad y probarla con las DOS formas del dato de entrada (ruta posix y win32, LF y CRLF, ruta directa y via symlink), lo que falla en cualquier sistema. Para tmpdirs, usar `mkCanonicalTmpDir` de `tests/support/tmp.ts` en todo test que compare una ruta contra la que devuelve el producto: el producto canonicaliza (`findProjectRoot` hace `realpathSync`) y el test debe hablar de la misma ruta. macOS se reproduce en Linux con `TMPDIR=<dir-symlinkeado> npx jest`.

- **verify-fix-by-revert-not-just-green:** despues de escribir un fix + su regression test, revertir SOLO el fix (dejando el test nuevo) y confirmar que ese test especifico falla, luego restaurar. Una suite verde es compatible con un test que nunca ejercita la linea que arregla el bug: mock que bypasea la ruta real, condicion que no dispara en el fixture, assert sobre el sintoma equivocado. *(≥5 veces, siempre encontrado por una revision posterior — nunca por el autor del fix.)* **Variante mas cara: el fix aterriza en la funcion EQUIVOCADA cuando existen dos hermanas de proposito similar** — un mensaje agregado a `renderReport` (que usa solo `awm init`) en vez de a `renderProviderReport` (la que invoca `awm doctor`), con el test nuevo en verde porque testeaba la funcion equivocada directamente. La contramedida no es "escribir mas tests": ante dos funciones de nombre o forma similar, confirmar explicitamente cual invoca el comando real ANTES de decidir donde aplica el fix.

- **duplicate-side-effect-across-composed-functions:** cuando la misma condicion de gateo (`if (isWindowsNative()) emit(msg)`) vive en mas de una funcion que terminan llamandose juntas en la misma secuencia, el efecto se dispara una vez POR CADA funcion compuesta, no una vez por comando. *(`awm init` disparaba el mismo caveat de Windows 3 veces; cada funcion se testeaba aislada, nunca el flujo completo.)* Al agregar un efecto lateral gateado por una condicion global a una funcion que se compone con otras, verificar CUANTAS veces se ejecuta esa condicion en un flujo real de punta a punta.

  **Variante por rama de dispatcher faltante:** un efecto lateral nuevo agregado a una funcion compartida hereda TODOS los call-sites existentes de esa funcion, **incluidos los que un dispatcher ya deberia haber salteado pero no saltea por una rama faltante**. *(`regenerateGlobalContext` no tenia rama para `cc-settings-merge`, asi que `collectAndWarn()` imprimia diagnosticos duplicados y dejaba un `awm-context.md` huerfano.)* Verificar el dispatcher completo, no solo el call-site que la task esta tocando.

- **assert-call-order-not-just-existence:** cuando un orquestador debe ejecutar pasos en orden y el fake graba comandos en `calls[]`, verificar con `expect(calls.indexOf('A')).toBeLessThan(calls.indexOf('B'))` — no con `toContain`, que pasa aunque los pasos se reordenen. Aplica a `writePackageVersion` antes de `git commit`, `WRITE_NPMRC` antes de `npm publish`, `npm publish` antes de `git push`.

- **dual-tmpdir-isolation:** cuando un test de comando escribe al home *y* clona repos, usar dos tmpdirs separados (`tmpHome` para HOME/AWM_HOME, `tmpWork` para repos fixture). Uno solo mezcla el home falso con los artefactos de trabajo y contamina entre tests. Patron: `beforeEach` crea ambos + sobreescribe `process.env.HOME` y `process.env.AWM_HOME` + `jest.resetModules()`; `afterEach` restaura y limpia; los modulos se importan con `require()` dentro del test, nunca al top-level. **Git fixtures con tags:** agregar `-c tag.gpgSign=false` al helper GIT — en maquinas con `tag.gpgSign=true` global la creacion de tags falla sin ese flag *(confirmado ×3)*.

- **module-level env vars / call-time preference:** las constantes derivadas de `process.env` (como `AWM_HOME`) se evaluan al `require`. **Alternativa preferida:** exportar funciones en vez de constantes — `export function awmHome() { return process.env.AWM_HOME || ... }` evalua en call-time y los tests sobreescriben `process.env` sin `jest.resetModules()`. Si el patron de constante es inevitable, dejar el comentario `// Evaluated at require-time — tests must use jest.resetModules() + late require() to pick up env overrides.`

- **stub-process-platform:** `Object.defineProperty(process, 'platform', { value: 'win32', configurable: true })`. El `configurable: true` es esencial — sin el, la restauracion en `afterEach` falla en silencio. Capturar el valor real antes (`const realPlatform = process.platform`) y restaurar con la misma llamada.

- **ansi-testing-inject-precolored:** los tests que construyen strings coloreados con `picocolors` para verificar stripping ANSI son vacuos en Jest: corre en non-TTY, `picocolors` devuelve texto plano, y el codigo de strip nunca se ejercita. Inyectar la sequence directamente (`'\x1b[32mhello\x1b[0m'`), o forzar `FORCE_COLOR=1` en el entorno del test.

- **eventemitter-fake-stdin:** para testear shells interactivos (raw-mode, key events) sin TTY real, usar `EventEmitter` como fake de `input`: emitir `'data'` con buffers de teclas y verificar lo escrito a `output`. Solo hace falta el contrato `{ on, removeListener, setRawMode?, pause? }`. Ver `tests/ui/picker-shell.test.ts`.

- **tdd-first-i18n:** para migraciones de strings (i18n, rebranding, renombrado de labels), actualizar primero los asserts al valor nuevo → verificar que fallen → traducir la fuente. Garantiza que no queden asserts huerfanos silenciados y que cualquier string omitido rompa el build. *(Confirmado en una migracion en→es de ~40 strings: el ciclo red→green detecto un cascade que un sweep directo habria silenciado.)*

- **windows-ci-gotchas:** tres patrones que solo se manifiestan contra Windows real, nunca contra `process.platform` mockeado:
  - **`ps`/`pgrep` en win32 resuelven al binario EMULADO de MSYS/Cygwin** (via Git for Windows), con su propia tabla de pids, ciega a procesos nativos spawneados por `CreateProcess`. Un `ps -p <pid>` de un proceso vivo sale con exit 1, indistinguible de una muerte real. **Usar `process.kill(pid, 0)`** (kernel via libuv), nunca `ps`/`pgrep`, para verificar procesos nativos en win32. *(Encontrado en `pidExistsNative`, `refIsAlive`, `groupIsGone`, `activitySnapshot` — el ultimo sobrevivio varias rondas de CI porque no estaba en la cadena de llamadas de los ya arreglados: auditar el archivo completo por el patron, no solo las funciones tocadas.)*
  - **Mocks que reemplazan la funcion ENTERA (`() => true`) rompen sondeos de existencia legitimos.** Un mock incondicional de `process.kill` para verificar "nunca se envia una señal real" tambien intercepta el `process.kill(pid, 0)` interno, y un pid diseñado para representar "muerto" aparenta estar vivo. Inspeccionar los args (`call[1] !== 0` filtra sondeos) o condicionar por pid — nunca `() => true` / `() => throw` sin narrowing.
  - **El modo de archivo en win32 SIEMPRE reporta `0o666`**, para archivos y para DIRECTORIOS. No hay bit ejecutable POSIX ni `0o700`/`0o777` para directorios. Una suposicion razonada ("las carpetas deberian tener el bit x") resulto falsa contra CI real.
  - Ninguno de los tres se descubre mockeando `process.platform`: tratar el mock local como cobertura de sintaxis, no de comportamiento, y presupuestar al menos una ronda de CI real antes de dar por cerrado codigo que toca procesos o filesystem con ramas win32.
  - **Ampliar un mecanismo de reintento que no converge es la respuesta equivocada.** `refIsAlive`/`pidExistsNative` con 3×50ms sobrevivio 2 corridas y fallo en la 3ra; ampliar a 10×100ms fallo en la corrida INMEDIATA siguiente, mismo sintoma — señal de que el sospechoso no era latencia de visibilidad. Lo que convergio fue reintentar la INSTANCIA completa del spawn a nivel de test, no la misma consulta sobre el mismo pid. Regla: si ampliar un mismo mecanismo no converge al segundo intento, cuestionar QUE se esta reintentando antes de ampliarlo una tercera vez (`systematic-debugging`, Fase 4.5).

- **external-tool-reliability-needs-multiple-real-confirmations:** cuando una decision de seguridad o liveness se delega a una herramienta externa nueva, una sola corrida exitosa —aunque sea contra CI real— no alcanza como evidencia de confiabilidad. *(`refIsAlive` en win32 delego identidad a WMI via `powershell.exe`; la primera corrida real dio un falso negativo sobre un proceso vivo, mientras `process.kill(pid, 0)` llevaba varias corridas limpias. Se revirtio al kernel, aceptando el gap de reciclado de PID como conocido.)* Regla: exigir ≥2-3 corridas reales limpias antes de promover una fuente nueva a gate de decision irreversible; mientras tanto, preferir la fuente probada aunque tenga un gap acotado — un gap documentado le gana a un falso negativo no detectado.

## Patrones de diseño de API

- **default-arg-seam:** en funciones multi-root (`discoverSkills`, `discoverAllBundles`, etc.), pasar `roots = contentRoots()` como parámetro default en vez de llamar `contentRoots()` en el cuerpo. Esto da compatibilidad hacia atrás en todos los call-sites existentes (sin cambios) y permite inyectar roots en tests sin tocar `~/.awm`. El default queda abierto a enriquecerse (nuevos roots, overrides) sin modificar a los consumidores existentes.

- **contentRoot stamp en discovery:** estampar `contentRoot` sobre cada artefacto en el momento del discovery, no en el momento del install/uso. Los consumidores downstream no necesitan saber de qué registry proviene el artefacto — el path absoluto ya los guía al lugar correcto.

- **injected-logger:** cuando una función necesita emitir warnings o mensajes al usuario, recibir el logger como argumento (`fn(log: (msg: string) => void)`) en vez de llamar `console.warn()` directamente. Ventaja: la función es pura (sin side effects de I/O), testeable sin capturar stdout, y reutilizable con cualquier output channel. Patrón: `noteWindowsCaveat((m) => console.log(pc.dim(m)))` en el call-site.

- **pure-render-io-split:** al construir un selector/picker interactivo, separar completamente el render puro (`(state, width) → string[]`) del shell I/O (`onData → dispatch → redraw`). El render puro es 100% testeable sin terminal; el shell I/O queda delgado y se aísla con injectable IO. Patrón: `defaultIO = () => ({ input: process.stdin, output: process.stdout })` como función lazy (no en import-time) + seam de default argument en la función pública. Confirmado en `src/ui/picker-view.ts` + `picker.ts`.

- **hoist-per-root-io:** en funciones que iteran sobre roots y dentro de cada root iteran sobre artefactos, hacer el I/O de por-root (p.ej. `readRegistryManifest(root)`) **fuera del loop interno**, no dentro. Multiplicar lecturas de disco por artifact es innecesario. Patrón: `for (const root of roots) { const overrides = readRegistryManifest(root); for (const a of artifacts(root)) { /* usa overrides */ } }`. Confirmado en más de una revisión de code-quality.

- **atomic-add para directorios administrados:** el flujo correcto para un comando que agrega a un directorio gestionado es: operación costosa (clone/fetch) → validar → verificar colisiones → escribir config. Fallo en cualquier paso = limpiar el directorio creado (`rmSync(dest, {recursive:true,force:true})`) + no escribir config. Nunca escribir config antes de que la validación sea exitosa.

- **reuse-discovery-not-hand-rolled-scan:** al resolver un artefacto por nombre a través de múltiples content roots, delegar SIEMPRE a las funciones de discovery existentes (`discoverSkills`, `discoverAllBundles`, etc.) en vez de reimplementar un scan manual "primer root que matchea". Esas funciones ya encapsulan la semántica de colisión/override de `awm-registry.json` (`mergeEntry`: mismo nombre en 2 roots → error, salvo override declarado) — un scan manual la ignora silenciosamente, resolviendo al root incorrecto en instalaciones multi-registry sin avisar a nadie. Confirmado en `cli/src/core/export/resolve.ts`: la primera versión de `locate()` era un scan hand-rolled; el fix la reescribió para delegar en `discoverSkills(roots)`.

- **grep-before-you-write-a-helper:** antes de escribir una función local que compute algo que otro módulo del mismo plan probablemente ya calcula (un path físico, una sanitización de timestamp, un try/catch de resolución de agentes), correr `grep -rn "<nombre-candidato>\|<lógica equivalente>" src/` primero. Confirmado repetidamente, en planes distintos: `install-planner.ts` y `core/init/mutation-targets.ts` mantuvieron dos copias byte-idénticas de `physicalTarget` (unificadas exportando una y reusándola); `sanitizeTransactionTimestamp` existió duplicada con reglas de sanitización DIVERGENTES entre `applyInstallPlan` y `beginBackupSession` (una silenciosamente más estricta que la otra); el boilerplate de `resolveAgentTargets` + try/catch se repitió en 6 call-sites hasta extraerse en `resolveAgentTargetsOrError`. El costo de la duplicación no es solo estético — cuando diverge, es un bug latente invisible hasta que alguien edita solo una copia. **Otra instancia:** el implementador de `checkSensorsBaseline` (`cli/src/commands/preflight/checks.ts`) copió al pie de la letra la fórmula `enabled`/`total` de `checkManifest`, en el MISMO archivo, en vez de extraerla — el sibling estaba a 100 líneas de distancia, visible sin necesidad de grep. Un manifest con un sensor `null` ya crashea `checkManifest`; la duplicación dejaba la misma mina en `checkSensorsBaseline`, lista para explotar el día que alguien blindara una copia y no la otra. Curado extrayendo `countEnabledSensors()` compartida. La duplicación no necesita cruzar archivos ni distancia para calificar — con el original a la vista en el mismo archivo alcanza.

## Patrones de implementación

- **execFileSync-not-execSync:** usar `execFileSync(cmd, args[])`, nunca `execSync('cmd arg1 arg2')`. `execSync` pasa la string a la shell y cualquier arg con espacios, comillas o metacaracteres puede alterar el comando. Aplica a todos los wrappers de git/npm/awm de este repo.

- **shell-quote-verify-against-primary-source:** cuando `execFileSync` no es viable (el operador escribe sintaxis de shell real en el `cmd` de `.awm/sensors.json`, asi que `spawn(cmd, {shell:true})` es deliberado — ver `exec.ts`) y hay que interpolar un valor externo, **verificar el escaping contra la fuente primaria antes de implementar — nunca por intuicion ni copiando un ejemplo similar.** `shellQuote()` (`changed.ts`) se equivoco TRES veces en el mismo release: comillas embebidas dobladas `""` en vez de `\"`; backslashes no duplicados antes de una comilla (corrompe filenames terminados en `\`; regla exacta en `learn.microsoft.com/en-us/cpp/c-language/parsing-c-command-line-arguments`); y los operadores de `cmd.exe` (`& | < > ^ %`) que NO quedan neutralizados por el wrapping `"..."` — inyeccion real, la misma clase que BatBadBut/CVE-2024-27980. La leccion no es "cuidado con el quoting": es que la intuicion sobre `cmd.exe` es sistematicamente incorrecta, hasta para el autor de la investigacion de referencia. **Cuando escapar de forma confiable no esta garantizado, la resolucion correcta es rechazar el input peligroso y degradar a la operacion completa** (`hasUnsafeWin32Chars` + fallback a `config.cmd` en `run.ts`), no intentar escapar mejor — el mismo camino que tomo el equipo de seguridad de Node.

- **prefer-stdlib-over-hand-rolled-parsing:** para formatos con reglas no triviales (URLs, JSON externo, YAML), preferir el parser estandar antes que una regex, un tipo TypeScript sin validacion runtime, o una suposicion hand-rolled sobre cobertura. El parser estandar ya resolvio los edge cases contra la especificacion real; la alternativa tolera en silencio las formas que el autor no imagino. *(×4 en releases distintas, todas encontradas por revision posterior — nunca por el autor.)* Los tres modos de falla, cada uno con su fix:
  1. **Regex sobre una URL** — `extractHost()` capturaba el bloque `userinfo@host:puerto` entero, asi que un remote `https://user:gitlab@example-host.com/...` (patron real de inyeccion de credenciales en CI) se clasificaba por una substring del token, no del host. Fix: `new URL(remote).hostname`, con una regex acotada SOLO para la sintaxis SCP de git (`user@host:path`), que no es una URL valida.
  2. **Tipo TS sobre `JSON.parse()`** — `parseRuffOutput`/`parseShellcheckOutput` declaraban `RuffMessage[]` y leian campos directo. El tipo es una promesa que el compilador no verifica en runtime: `'{}'`, `'null'`, `'42'` o un elemento `null` en el array son JSON valido que no calza, y crasheaban el sensor run COMPLETO. Fix: `Array.isArray(parsed)` + guardas de forma por elemento ANTES de leer propiedades, degradando a `[]`/skip.
  3. **Cobertura de un stdlib asumida en vez de verificada** — `yamlString()` confiaba en que `JSON.stringify` escapa "control bytes"; solo escapa 0x00-0x1F, y **0x7F (DEL) no esta en el conjunto que JSON exige escapar**, asi que sobrevivia sin escapar dentro de la scalar citada, violando el c-printable de YAML 1.2. Aca el mecanismo SI era stdlib: la cobertura de un mecanismo estandar sobre un rango completo no se asume, se verifica contra el rango real que hay que cubrir.

  La contramedida no es "revisar mejor a mano" — ya se intento las cuatro veces. Es preferir una implementacion ya verificada contra la especificacion cuando existe, y cuando no existe, validar forma o cobertura en runtime o empiricamente. Un tipo TS sobre `JSON.parse()`, o un comentario que afirma "X ya escapa Y", nunca son garantia — son una nota para el autor.

- **defensive-guard-consistency:** al agregar una guarda defensiva (`?? {}`, chequeo de null, un caso "N/A" tratado como satisfecho), buscar TODAS las funciones hermanas que leen el mismo campo o comparten la misma condicion y aplicar la misma guarda ahi tambien — no solo en la que se esta editando. *(×5. `checkManifest` toleraba `manifest.sensors ?? {}` pero sus hermanas `computeSensorStatus`/`runSensors` crasheaban con `sensors: null`; `gatherMachine` tenia el mismo bug en `devCore` y en `ambient`, y el fix inicial solo cubrio el primero; `description:` del frontmatter se parseaba a mano en CUATRO lugares con copias incompletas.)*

  **Corolario: unificar a medias es peor que no unificar.** Mientras discovery ya resolvia bien el campo y `parseCanonicalAgent` seguia roto, el picker mostraba la descripcion correcta y el install explotaba despues, con un mensaje que no mencionaba el motivo. Si dos caminos leen el MISMO archivo, o se arreglan juntos o quedan divergentes de forma mas confusa que el bug original.

  **Grep de verificacion tras un fix de este tipo** — exhaustivo y ANTES de darlo por cerrado, no delegado a un reviewer posterior: buscar toda ocurrencia del campo o condicion guardada (`grep -rn "\.sensors\b" cli/src`, `grep -rn "skillsDir\|skill\.global" cli/src/core/diagnostics cli/src/core/init`, `grep -rn "description\s*:" cli/src`) y confirmar que cada computo relacionado tiene la misma guarda.

  **Corolario que supera al grep:** el grep encuentra los hermanos de HOY, no el cuarto sitio que alguien escribe el mes que viene sin haber leido esto. *(Tres sitios comparaban rutas con `realpathSync(a) !== realpathSync(b)`; en Windows el mismo directorio tiene dos grafias — 8.3 vs nombre largo, `\` vs `/` — y la comparacion negaba un worktree propio: 18 tests rojos SOLO en Windows.)* Lo que cierra la clase es un **guard estructural sobre la FORMA** (`tests/structural/path-identity-not-string-compare.test.ts` prohibe el patron en todo `src/`, sin enumerar sitios), validado por revert. Regla: cuando el mismo defecto aparece en ≥3 hermanos, el fix no esta completo hasta que existe un guard que rechace la forma.

  **Aplica igual a COBERTURA DE TEST, no solo a guardas de codigo:** que una garantia este probada en un caller no implica que un caller hermano —agregado despues, reusando la misma funcion— tenga su propia red. *(La garantia fail-safe de R5.1 estaba regression-testeada para el path de `InjectionOrchestrator`; `installClaudeHook`/`resyncClaudeHookFiles`, el path de mayor riesgo, reusaba `collectAndWarn` y cumplia la garantia en el codigo real, pero nada la fijaba con un test propio.)* Cada caller de alto riesgo necesita su test dedicado, no heredar cobertura por asociacion.

- **differential-test-contra-implementacion-de-referencia:** cuando el repo parsea a mano un formato que tiene parser de referencia disponible (YAML, TOML, semver, globs), el ancla correcta NO es una tabla de casos escritos a mano con sus valores esperados — es un test que compara la implementacion propia contra el parser real sobre una lista de entradas. *(El parser de `description` tenia tests a mano en verde y paso DOS revisiones; un test diferencial contra `js-yaml` encontro cuatro divergencias reales en minutos.)* Los valores esperados no pueden envejecer hacia una expectativa equivocada, y agregar un caso cuesta una linea. El parser de referencia va como **devDependency** — la regla de cero dependencias de runtime queda intacta, y este test es lo que la hace defendible en vez de un acto de fe.

- **best-effort-catch-comment:** un `catch {}` vacio es indistinguible de un olvido. Cuando es deliberado, comentar el tradeoff: `// best-effort: <que hace el fallback>; <que se pierde respecto al happy path>`. Previene que un refactor futuro agregue un re-throw "para limpieza" que rompa el comportamiento.

- **gate-order-annotation:** cuando el orden de ejecucion esta dictado por una regla de CONSTITUTION (p.ej. "gates de contrato antes de early-exits"), citarla inline: `// CONSTITUTION: gates de contrato antes de early-exits`, inmediatamente antes del primer gate del bloque. Permite verificar cumplimiento sin buscar la regla y previene reordenamientos accidentales. *(Confirmado en mas de un release: una regresion por early-exit antes del gate de pins, y el gate `minCliVersion` colocado antes del early-exit de extensions vacias.)*

## Patrones de documentación

- **verify-cmd-source-before-documenting:** cuando se documenta un comando AWM (storage target, keywords aceptados, flags), verificar `cli/src/commands/<cmd>.ts` antes de escribir. La narrativa puede sobrevivir spec-review y code-quality-review sin que nadie cheque el código fuente. En una revisión de documentación de comandos, `awm pin` fue documentado con keyword incorrecto (`base` vs `baseline`) y storage location incorrecta (`profile.json` vs `~/.awm/preferences.json`); ambos pasaron las dos primeras rondas de review. **Confirmado de nuevo en R1** (`docs/guides/authoring-a-registry-with-an-orchestrator.md`, plan `2026-08-21-registry-declared-orchestrators-r1-plan`): CINCO errores factuales/procedimentales distintos en una guía nueva de ~140 líneas — un comando inventado (`awm registry status`, que no existe; el real es `awm registry list`), un paso de `git init` faltante antes de `awm registry add` (que requiere un repo git real), un `git push origin` que asume un remote nunca configurado antes en la guía, un nombre de registry (`--name mi-proceso`) que diverge del directorio `mi-registry` de una sección anterior, y un paso de instalación de bundle (`awm add`/`--install-all`) nunca mencionado pese a ser necesario en uso no interactivo. Ninguno lo atrapó la revisión de la tarea que creó la guía — todos salieron en una QA posterior que ejecutó los comandos reales contra un CLI aislado, no leyendo la prosa.

- **runbook-as-script:** para workstreams que combinan documentación + verificación manual, escribir el doc como hipótesis y ejecutarlo literalmente como test. Las divergencias se corrigen en el doc (no en el tool); el entregable es un doc verificado contra realidad. Confirmado varias veces en la misma revisión (mensajes de error, mecánica de pin, secuencia de onboarding — todas corregidas contra el binario real durante la verificación): escribir ejemplos de output de CLI sin verificar contra el binario real es la fuente de error más común en documentación de comandos.

## Release / publish

- **El release del CLI es automático en `main` — no hay paso manual de `npm publish`.** `.github/workflows/release.yml` (trigger `push` a `main`) buildea `cli/` y corre `cli/src/release/index.js`: bump por conventional commits + `npm publish` vía OIDC Trusted Publisher + commit de bump con `[skip ci]`. **Antes de decir "publicá a mano" o de proponer/crear un workflow de release paralelo, verificá que `release.yml` ya lo cubre** — ya existe y es completo. El nivel de versión sale del prefijo de conventional commit del merge; regla no-negociable en `CONSTITUTION.md` → "Release del CLI".

## Auto-verificación del CLI (dogfooding)

- **`awm` en el PATH puede ser una instalación global publicada, desconectada del working tree que estás editando.** Al desarrollar este mismo CLI, el binario que resuelve `which awm` suele venir de una instalación global de npm (`npm i -g agentic-workflow-manager`) con una versión publicada anterior — no del código que acabás de cambiar en `cli/src/`. Correr `awm sensors run` "en carne propia" contra ese binario prueba una versión vieja, no tu diff: un bug ya arreglado localmente (ej. exit 127 clasificado como `fail`) puede seguir viéndose roto (`skipped`) porque el binario global nunca se actualizó. Confirmado comparando la salida de `awm sensors run` (global) contra `node dist/src/index.js sensors run` (build local): resultados distintos para el mismo sensor. **Al auto-verificar este CLI durante su propio desarrollo, siempre `npm run build && node dist/src/index.js <comando>` desde `cli/` — nunca confiar en `awm` bare del PATH.**

## Subagentes concurrentes y git

- **Nunca despachar subagentes con acceso a Bash en paralelo sobre el mismo working tree si alguno puede correr `git checkout <ref> -- <path>` (u otro comando que mute el índice/working tree) para "mirar una versión vieja".** Caso confirmado: varios subagentes de QA corrieron en paralelo sobre el mismo checkout; uno de ellos ejecutó `git checkout <commit-base> -- .` para comparar sensores contra una baseline preexistente, y su restore posterior quedó incompleto — probablemente por carrera con los `git diff`/`git show` de sus hermanos concurrentes tocando el mismo working tree al mismo tiempo. El resultado: varios archivos revertidos a una versión anterior a tareas ya completadas, silencioso hasta que un `git status` de rutina lo mostró. El historial de commits (HEAD, reflog) nunca se corrompió — el daño fue puramente de working tree + índice, y `git checkout HEAD -- .` lo revirtió limpio una vez detectado.
  - **Para inspeccionar contenido histórico de un archivo sin tocar el working tree, usar `git show <ref>:<path>` (lee, no muta) en vez de `git checkout <ref> -- <path>` (muta índice y working tree).** Es la causa raíz evitable: `git show` responde la misma pregunta ("¿qué decía este archivo en tal commit?") sin ningún riesgo de dejar el árbol en un estado intermedio si el proceso se interrumpe o compite con otro.
  - **Si un subagente necesita comparar "antes vs. después" de forma más elaborada que un diff (ej. correr el binario contra ambas versiones), aislarlo en un worktree separado (`git worktree add`), nunca mutar el checkout compartido.**
  - **El controlador debe verificar `git status --short` después de cualquier ronda de subagentes paralelos con acceso a Bash, antes de confiar en sus reportes** — no asumir que "reportó DONE" implica que el working tree está en el estado esperado. Este chequeo fue lo único que detectó la corrupción en el caso de arriba; nada en los reportes de los subagentes involucrados la mencionaba.
  - **`git commit --amend --reset-author` (el remedio que sugiere el stop-hook de firma cuando detecta commits sin firmar) resetea el `AuthorDate` Y el `CommitDate` al momento del amend — no solo la identidad.** Un `git rebase --exec "git commit --amend --no-edit --reset-author"` sobre varios commits sin firmar (para resolver la advertencia del hook) colapsó sus timestamps reales (minutos de trabajo real de subagentes distintos) a segundos de diferencia entre sí — el momento en que corrió el propio rebase, no el momento original de cada commit. Un lens de QA posterior, razonando sobre esos timestamps ya corrompidos, concluyó erróneamente que pasos de verificación que tardan tiempo real (sleeps de sonda, ciclos RED/GREEN) nunca pudieron haber ocurrido — falso positivo con causa raíz identificable, no evidencia real de trabajo no hecho. **Si el timing real de los commits importa para auditoría/forense futura, o si una QA de esta rama va a correr después de un rebase de firma, revisar el `AuthorDate` real (`git log --format='%ad' --date=iso-strict`) antes de tomar timestamps como prueba de cuándo ocurrió el trabajo — y, si es evitable, considerar firmar en el momento del commit original en vez de corregir con un rebase masivo después.**

## Ledger y trazabilidad

- **`awm ledger add` puede correr dos veces para el mismo hallazgo — el controlador debe leer `awm ledger list` completo, no confiar en el conteo de `awm ledger recurring` a ciegas.** Confirmado ≥4 veces en un solo release: entradas con `phase`+`signature`+`desc` byte-idénticos y timestamps a milisegundos de diferencia, más entradas de prueba sueltas que algún subagente dejó al verificar que `awm` respondía antes de loguear el hallazgo real. El riesgo: `awm ledger recurring --min 2` cuenta duplicados exactos como si fueran 2 ocurrencias reales, lo que puede empujar de forma espuria un hallazgo trivial a la categoría "sistémico" en el triage de `harness-retro` modo desatendido. Mitigación: reconciliar contra `awm ledger list` (contenido real) en cada paso, no contra el resumen en prosa de cada subagente — mismo principio que "el controlador debe verificar `git status --short`" arriba, aplicado al ledger en vez del working tree.

- **Depurar directamente contra evidencia real (logs de CI, stack traces) sin invocar formalmente el skill `systematic-debugging` deja el ledger vacío incluso cuando hay hallazgos reales — y un ledger vacío con hallazgos reales es en sí mismo el hallazgo de retro** (ver "Empty-ledger consistency check" del skill `harness-retro`). Caso confirmado: un ciclo completo de varias rondas de fixes contra CI real de `windows-latest` (~137 fallos → 0, incluida una reversión arquitectónica documentada en el propio código fuente) produjo **cero** entradas en el ledger, porque el trabajo se hizo leyendo logs de CI y parcheando directamente, no a través de una invocación explícita de `systematic-debugging` (que es quien emite `awm ledger add --phase debugging` al confirmar una causa raíz). `harness-retro` detectó el vacío contra la evidencia de la sesión y tuvo que reconstruir el registro post-hoc. Regla: al confirmar una causa raíz mientras se depura directamente contra evidencia (sin pasar por el skill), emitir el `awm ledger add --phase debugging --polarity finding ...` de todos modos — el skill formaliza el paso, pero la obligación de loguear no depende de invocarlo.

## Layout del repo y de la instalación

- **Este repo** contiene solo el CLI TypeScript (`cli/`). El contenido (skills, bundles, sensor-packs, hooks) vive en repos externos: `awm-baseline-registry` y `awm-documentation-registry`.
- **No hay `registry/` en este repo** ni `~/.awm/cli-source/`. El concepto `cli-source` fue eliminado.
- **Layout de instalación:** `~/.awm/registries/<name>/` — cada registry configurado se clona aquí (ej. `~/.awm/registries/baseline/`). Los skills se instalan como symlinks hacia esos paths.
- **Descubrimiento de contenido:** `contentRoots()` devuelve los paths bajo `~/.awm/registries/` según la config. No hay constante fija de `baseRoot` ni de `cliSource`.
