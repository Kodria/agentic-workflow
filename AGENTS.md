# AGENTS.md — Guía de mantenimiento de AWM

Esta es la guía de mantenimiento de este repo (el CLI de AWM) — no la función del propio CLI que genera un `AGENTS.md` para *otros* proyectos (ver `cli/src/core/context/strategies/`, `cli/src/core/renderers/`). Cada entrada de abajo es un patrón de ingeniería confirmado contra el código real de este repo, curado con la misma disciplina merge-and-prune que aplica `harness-retro` sobre cualquier proyecto: fusionar lecciones nuevas en las secciones existentes, podar lo que ya no aplica, nunca apilar un log crudo por encima. La procedencia detallada de cada hallazgo (qué release, qué fecha, qué commit) vive en el historial de git y en `docs/plans/` — este documento guarda la lección generalizable y accionable, no el diario de la sesión que la produjo. Todo agente que trabaje en este repo debe leerlo antes de tocar código.

---

## Patrones de testing

- **verify-fix-by-revert-not-just-green:** después de escribir un fix + su regression test, no confiar en que "la suite completa está verde" prueba que el test cubre el fix — revertir SOLO el fix (dejando el test nuevo) y confirmar que ese test específico falla, luego restaurar. Una suite verde es compatible con un test que nunca ejercita la línea que arregla el bug (mock que bypasea la ruta real, condición que no dispara en el fixture, assert sobre el síntoma equivocado). Confirmado ≥5 veces en releases distintas, siempre encontrado por una revisión posterior — nunca por el propio autor del fix. **Variante más cara: el fix aterriza en la función EQUIVOCADA cuando existen dos funciones hermanas de proposito similar** — en R7, un mensaje de diagnóstico se agregó a `renderReport` (usada solo por `awm init`) en vez de a `renderProviderReport` (la que `awm doctor` realmente invoca); el test nuevo pasaba en verde porque testeaba `renderReport` directamente, dando falsa confianza mientras el comando real (`awm doctor`) nunca mostraba el mensaje — 3 lentes independientes de QA lo encontraron por separado. La contramedida no es "escribir más tests" (ya había tests, solo no cubrían la función/ruta real) — es, ante DOS funciones de nombre/forma similar, confirmar explícitamente cuál es la que el comando real invoca antes de decidir dónde aplica el fix, y agregar el paso de revert-and-rerun como parte de la verificación del propio fix, no delegarlo a que alguien más lo note después.

- **duplicate-side-effect-across-composed-functions:** cuando la misma condición de gateo (`if (isWindowsNative()) emit(msg)`) vive en más de una función que terminan llamándose juntas en la misma secuencia (ej. `render(before)` + `render(after)` dentro de un mismo comando), el efecto se dispara una vez POR CADA función compuesta, no una vez por comando — un mensaje pensado para aparecer una sola vez termina repitiéndose N veces. Confirmado en R7: `awm init` disparaba el mismo caveat de Windows 3 veces en una sola corrida (una llamada directa + 2 embebidas en el resumen antes/después). Ningún test lo cazó porque cada función se testeaba aisladamente, nunca el flujo completo del comando real. Al agregar un efecto lateral gateado por una condición global a una función que se compone con otras, verificar CUÁNTAS veces se ejecuta esa condición en un flujo real de principio a fin — no solo que cada función individual la evalúe correctamente.

- **assert-call-order-not-just-existence:** cuando un orquestador debe ejecutar pasos en un orden específico y el fake graba comandos en un array `calls[]`, verificar el orden con `expect(calls.indexOf('A')).toBeLessThan(calls.indexOf('B'))` — no solo con `expect(calls).toContain('A')`. Un `toContain` pasa aunque los pasos se reordenen. Aplicar a cualquier secuencia donde el orden importa: ej. `writePackageVersion` antes de `git commit`, `WRITE_NPMRC` antes de `npm publish`, `npm publish` antes de `git push`.

- **dual-tmpdir-isolation:** cuando un test de comando escribe al home *y* clona repos, usar dos tmpdirs separados (`tmpHome` para HOME/AWM_HOME, `tmpWork` para repos fixture). Un solo tmpdir mezcla el "home falso" con los artefactos de trabajo y provoca contaminación cruzada entre tests. Patrón completo: `beforeEach` crea ambos tmpdirs + sobreescribe `process.env.HOME` y `process.env.AWM_HOME` + llama `jest.resetModules()`; `afterEach` restaura y limpia. Todos los módulos se importan con `require()` dentro del test (no al top-level del archivo). **Git fixtures con tags:** agregar `-c tag.gpgSign=false` al helper GIT (`execSync(\`git -c user.email=t@t.t -c user.name=t -c tag.gpgSign=false ...\`)`); en máquinas con `tag.gpgSign=true` global la creación de tags falla sin este flag (confirmado necesario, ×3 revisiones independientes).

- **module-level env vars / call-time preference:** las constantes derivadas de `process.env` (como `AWM_HOME`) se evalúan al momento del `require`. Al crear un módulo con este patrón, agregar el comentario `// Evaluated at require-time — tests must use jest.resetModules() + late require() to pick up env overrides.` para que futuros implementadores de tests no lo descubran a las malas. **Alternativa preferida:** exportar funciones en vez de constantes — `export function awmHome() { return process.env.AWM_HOME || ... }` evalúa en call-time; los tests pueden sobreescribir `process.env` en `beforeEach/afterEach` sin `jest.resetModules()`.

- **stub-process-platform:** para stubbear `process.platform` en tests usar `Object.defineProperty(process, 'platform', { value: 'win32', configurable: true })`. El flag `configurable: true` es esencial — sin él, la restauración en `afterEach` falla silenciosamente. Capturar el valor real antes de los tests (`const realPlatform = process.platform`) y restaurar en `afterEach` con la misma llamada.

- **ansi-testing-inject-precolored:** los tests que construyen strings coloreados con `picocolors` para verificar stripping ANSI son vacuos en Jest: Jest corre en non-TTY, `picocolors` devuelve strings planos sin sequences ANSI, y el código de strip nunca se ejercita. Inyectar la sequence directamente: `'\x1b[32mhello\x1b[0m'` en vez de `pc.green('hello')`. Si el test mide `displayWidth` de strings que vendrán coloreados en producción, usar strings ANSI hardcodeados o forzar `FORCE_COLOR=1` en el entorno del test.

- **eventemitter-fake-stdin:** para testear shells interactivos (raw-mode, key events) sin un TTY real, usar `EventEmitter` como fake de `input`: emitir `'data'` con buffers de teclas, verificar lo escrito a `output`. No se necesita stdin global ni `process.stdin` — solo el contrato `{ on, removeListener, setRawMode?, pause? }`. Patrón confirmado en `tests/ui/picker-shell.test.ts`.

- **tdd-first-i18n:** para migraciones de strings (i18n, rebranding, renombrado de labels), actualizar primero los asserts de tests al nuevo valor → verificar que fallen (red) → traducir la fuente (green). Esto garantiza que no quedan asserts huérfanos silenciados y que cualquier string omitido en el sweep rompe el build en vez de pasar desapercibido. Confirmado en una migración i18n de ~40 strings del CLI (en→es): el ciclo red→green detectó un cascade en `init.test.ts` que un sweep directo habría silenciado.

- **windows-ci-gotchas (confirmado en la primera corrida real del suite completo contra `windows-latest`):** tres patrones que solo se manifiestan contra Windows real, nunca contra `process.platform` mockeado localmente:
  - **`ps`/`pgrep`, cuando resuelven en el PATH en win32 (típicamente vía Git for Windows), son el binario EMULADO de MSYS/Cygwin — tienen su propia tabla de pids, ciega a procesos nativos spawneados vía `CreateProcess`.** Un `ps -p <pid>` para un proceso nativo real y vivo sale con exit 1 ("no existe" según la vista emulada), indistinguible de una muerte real confirmada. Encontrado en varios sitios de código de producción (`pidExistsNative`, `refIsAlive`, `groupIsGone`, `activitySnapshot`, todos en `core/journal/`) — el último caso sobrevivió más de una ronda de CI real porque no forma parte de la cadena de llamadas de las funciones ya arregladas, hasta que se auditó el archivo completo por el patrón, no solo las funciones ya tocadas. Alternativa multiplataforma confiable, respaldada directamente por el kernel vía libuv: `process.kill(pid, 0)` (existencia) — nunca `ps`/`pgrep` para verificar procesos nativos en win32.
  - **Mocks de `process.kill`/`execFileSync` que reemplazan la función ENTERA (`() => true` / `() => { throw ... }` sin inspeccionar los args) rompen sondeos de existencia legítimos (signal 0) que la implementación agrega DESPUÉS de escrito el test.** Un test que mockea `process.kill` para verificar "nunca se envía una señal real" con `mockImplementation(() => true)` incondicional también intercepta el sondeo interno `process.kill(pid, 0)` de `pidExistsNative` — hace que un pid diseñado para representar "muerto" aparente estar vivo. Fix: inspeccionar el segundo argumento (`call[1] !== 0` filtra sondeos de existencia) o condicionar el mock por pid/args específicos, nunca `() => true`/`() => throw` sin narrowing.
  - **El modo de archivo en win32 (`fs.chmod`/`stat().mode`) SIEMPRE reporta `0o666`, tanto para archivos como para DIRECTORIOS — nunca hay bit ejecutable POSIX, ni `0o700`/`0o777` para directorios.** Una suposición razonada ("las carpetas deberían tener el bit x") resultó incorrecta contra evidencia real de CI — verificar contra la corrida real, no contra el razonamiento sobre cómo "debería" comportarse un filesystem.
  - Ninguno de estos tres se descubre mockeando `process.platform` localmente — los tres requirieron al menos una corrida real en `windows-latest` CI para salir a la luz. Al escribir/revisar código que toca procesos o filesystem con ramas win32, tratar el mock local como cobertura de sintaxis, no de comportamiento real — y presupuestar al menos una ronda de CI real antes de dar por cerrado ese código.
  - **Incluso la fuente ya probada y "confiable" (`process.kill(pid, 0)`, kernel directo vía libuv) puede seguir dando falsos negativos bajo carga real de CI en el primer spawn del job — un presupuesto de reintento acotado no lo elimina, solo lo atenúa.** Encontrado en `refIsAlive`/`pidExistsNative`: un reintento de 3x50ms (100ms de espera) sobrevivió 2 corridas reales y luego falló en la 3ra; ampliarlo a 10x100ms (~900ms) falló en la corrida INMEDIATA siguiente, con el mismo síntoma exacto — evidencia de que seguir ampliando el mismo mecanismo (reintentar la MISMA consulta sobre el MISMO pid) tenía retornos decrecientes, y que el sospechoso real puede no ser latencia de visibilidad sino el proceso hijo terminando genuinamente temprano bajo ese runner (AV/Defender interviniendo un `node -e` recién lanzado — no confirmable sin Windows real). El fix que sí convergió fue de otra naturaleza: reintentar la INSTANCIA completa del spawn a nivel de test (una instancia nueva puede sobrevivir donde la anterior no lo hizo), no seguir subiendo el presupuesto de reintento de la consulta. Regla: si ampliar un mismo mecanismo de reintento no converge en el segundo intento, es señal de cuestionar qué se está reintentando (la consulta vs. la operación completa) antes de ampliarlo una tercera vez (systematic-debugging, Fase 4.5).

- **external-tool-reliability-needs-multiple-real-confirmations:** cuando una decisión de seguridad/liveness se delega a una herramienta externa nueva (ej. WMI/`Get-CimInstance` vía `powershell.exe`, en vez del kernel directo), una sola corrida exitosa —aunque sea contra CI real, no mockeada— no es evidencia suficiente de que la fuente sea confiable como gate. Caso confirmado: `refIsAlive` en win32 agregó una comparación de identidad completa vía WMI (motivada por cerrar un gap real de reciclado de PID); la primera corrida real en `windows-latest` mostró un falso negativo — un proceso node genuinamente vivo, recién spawneado, declarado muerto — mientras que `process.kill(pid, 0)` (kernel directo vía libuv) llevaba varias corridas reales consecutivas sin ningún falso negativo/positivo. Se revirtió a la fuente kernel-backed, aceptando el gap de reciclado de PID como conocido y documentado en vez de seguir confiando en WMI. Regla: exigir ≥2-3 corridas reales limpias (no solo tests mockeados) antes de promover una fuente nueva a gate de decisión irreversible (matar un proceso, declarar muerte); mientras tanto, usar la fuente ya probada aunque tenga un gap conocido y acotado — un gap documentado es preferible a un falso negativo no detectado en producción.

## Patrones de diseño de API

- **default-arg-seam:** en funciones multi-root (`discoverSkills`, `discoverAllBundles`, etc.), pasar `roots = contentRoots()` como parámetro default en vez de llamar `contentRoots()` en el cuerpo. Esto da compatibilidad hacia atrás en todos los call-sites existentes (sin cambios) y permite inyectar roots en tests sin tocar `~/.awm`. El default queda abierto a enriquecerse (nuevos roots, overrides) sin modificar a los consumidores existentes.

- **contentRoot stamp en discovery:** estampar `contentRoot` sobre cada artefacto en el momento del discovery, no en el momento del install/uso. Los consumidores downstream no necesitan saber de qué registry proviene el artefacto — el path absoluto ya los guía al lugar correcto.

- **injected-logger:** cuando una función necesita emitir warnings o mensajes al usuario, recibir el logger como argumento (`fn(log: (msg: string) => void)`) en vez de llamar `console.warn()` directamente. Ventaja: la función es pura (sin side effects de I/O), testeable sin capturar stdout, y reutilizable con cualquier output channel. Patrón: `noteWindowsCaveat((m) => console.log(pc.dim(m)))` en el call-site.

- **pure-render-io-split:** al construir un selector/picker interactivo, separar completamente el render puro (`(state, width) → string[]`) del shell I/O (`onData → dispatch → redraw`). El render puro es 100% testeable sin terminal; el shell I/O queda delgado y se aísla con injectable IO. Patrón: `defaultIO = () => ({ input: process.stdin, output: process.stdout })` como función lazy (no en import-time) + seam de default argument en la función pública. Confirmado en `src/ui/picker-view.ts` + `picker.ts`.

- **hoist-per-root-io:** en funciones que iteran sobre roots y dentro de cada root iteran sobre artefactos, hacer el I/O de por-root (p.ej. `readRegistryManifest(root)`) **fuera del loop interno**, no dentro. Multiplicar lecturas de disco por artifact es innecesario. Patrón: `for (const root of roots) { const overrides = readRegistryManifest(root); for (const a of artifacts(root)) { /* usa overrides */ } }`. Confirmado en más de una revisión de code-quality.

- **atomic-add para directorios administrados:** el flujo correcto para un comando que agrega a un directorio gestionado es: operación costosa (clone/fetch) → validar → verificar colisiones → escribir config. Fallo en cualquier paso = limpiar el directorio creado (`rmSync(dest, {recursive:true,force:true})`) + no escribir config. Nunca escribir config antes de que la validación sea exitosa.

- **reuse-discovery-not-hand-rolled-scan:** al resolver un artefacto por nombre a través de múltiples content roots, delegar SIEMPRE a las funciones de discovery existentes (`discoverSkills`, `discoverAllBundles`, etc.) en vez de reimplementar un scan manual "primer root que matchea". Esas funciones ya encapsulan la semántica de colisión/override de `awm-registry.json` (`mergeEntry`: mismo nombre en 2 roots → error, salvo override declarado) — un scan manual la ignora silenciosamente, resolviendo al root incorrecto en instalaciones multi-registry sin avisar a nadie. Confirmado en `cli/src/core/export/resolve.ts`: la primera versión de `locate()` era un scan hand-rolled; el fix la reescribió para delegar en `discoverSkills(roots)`.

- **grep-before-you-write-a-helper:** antes de escribir una función local que compute algo que otro módulo del mismo plan probablemente ya calcula (un path físico, una sanitización de timestamp, un try/catch de resolución de agentes), correr `grep -rn "<nombre-candidato>\|<lógica equivalente>" src/` primero. Confirmado repetidamente, en planes distintos: `install-planner.ts` y `core/init/mutation-targets.ts` mantuvieron dos copias byte-idénticas de `physicalTarget` (unificadas exportando una y reusándola); `sanitizeTransactionTimestamp` existió duplicada con reglas de sanitización DIVERGENTES entre `applyInstallPlan` y `beginBackupSession` (una silenciosamente más estricta que la otra); el boilerplate de `resolveAgentTargets` + try/catch se repitió en 6 call-sites hasta extraerse en `resolveAgentTargetsOrError`. El costo de la duplicación no es solo estético — cuando diverge, es un bug latente invisible hasta que alguien edita solo una copia. **Otra instancia:** el implementador de `checkSensorsBaseline` (`cli/src/commands/preflight/checks.ts`) copió al pie de la letra la fórmula `enabled`/`total` de `checkManifest`, en el MISMO archivo, en vez de extraerla — el sibling estaba a 100 líneas de distancia, visible sin necesidad de grep. Un manifest con un sensor `null` ya crashea `checkManifest`; la duplicación dejaba la misma mina en `checkSensorsBaseline`, lista para explotar el día que alguien blindara una copia y no la otra. Curado extrayendo `countEnabledSensors()` compartida. La duplicación no necesita cruzar archivos ni distancia para calificar — con el original a la vista en el mismo archivo alcanza.

## Patrones de implementación

- **execFileSync-not-execSync:** al ejecutar comandos externos desde Node.js, usar `execFileSync(cmd, args[])` en vez de `execSync('cmd arg1 arg2')`. `execSync` pasa la string a la shell — cualquier arg con espacios, comillas o metacaracteres puede alterar el comando. `execFileSync` con array de args evita el shell intermedio. Aplica a todos los wrappers de git/npm/awm en este repo.

- **shell-quote-verify-against-primary-source:** cuando `execFileSync`/array-args NO es viable (el CLI necesita que el operador escriba sintaxis de shell real en `.awm/sensors.json`'s `cmd`, así que `spawn(cmd, {shell:true})` es el mecanismo deliberado — ver `exec.ts`) y hay que interpolar un valor externo (filename) en el string resultante, **verificar el escaping contra la fuente primaria antes de implementar — nunca por intuición ni copiando un ejemplo similar.** `shellQuote()` (`changed.ts`) se equivocó de esta forma TRES veces en el mismo release antes de corregirse contra fuentes reales: (1) convención de escape de comillas embebidas incorrecta (doblado `""` en vez de backslash `\"`); (2) backslashes no duplicados antes de una comilla — corrompe filenames terminados en `\` (regla exacta: `learn.microsoft.com/en-us/cpp/c-language/parsing-c-command-line-arguments`); (3) los operadores de `cmd.exe` (`& | < > ^ %`) NO quedan neutralizados por el wrapping `"..."` — inyección de comandos real, confirmada contra la investigación BatBadBut/CVE-2024-27980 (el mismo bug que Node.js tuvo que parchear). La lección no es "cuidado con el quoting" genérico — es que la intuición sobre `cmd.exe` específicamente es sistemáticamente incorrecta, hasta para quien escribió la investigación de referencia (su propio autor dice no estar seguro de que su algoritmo de escape sea seguro). **Cuando escapar de forma confiable no está garantizado, la resolución correcta es rechazar el input peligroso y degradar a la operación completa/sin acotar** (ver `hasUnsafeWin32Chars` + fallback a `config.cmd` en `run.ts`), no intentar escapar mejor — el mismo camino que tomó el propio equipo de seguridad de Node para esta clase de vulnerabilidad.

- **prefer-stdlib-over-hand-rolled-parsing:** para parsear formatos con reglas no triviales (URLs, JSON externo, YAML), preferir el parser/módulo estándar del lenguaje o de la spec en vez de una regex, un tipo TypeScript sin validación runtime, o una suposición hand-rolled sobre cobertura — el parser estándar ya resolvió los edge cases (userinfo, puerto, IPv6 entre corchetes; formas de JSON válidas pero inesperadas; el rango exacto de bytes que hay que escapar) contra la especificación real, mientras que la alternativa hand-rolled tolera silenciosamente las formas que el autor no imaginó. Confirmado cuatro veces en la misma sesión, en releases distintas, cada una encontrada por revisión posterior (code-quality o el lens de robustez de `post-implementation-qa`) — nunca por el propio autor:
  1. `extractHost()` (`cli/src/commands/preflight/checks.ts`) necesitó dos rondas antes de estar bien: una regex hand-rolled hacía match contra la URL completa; el fix "por hostname" seguía capturando el bloque `userinfo@host:puerto` entero en vez de solo el host — un remote `https://user:gitlab@example-host.com/...` (patrón real de inyección de credenciales en CI) se clasificaba mal por contener la substring "gitlab" en el token, no en el host real. El fix final reemplazó la regex por `new URL(remote).hostname`, y mantuvo una regex acotada SOLO para la sintaxis SCP de git (`user@host:path`), que no es una URL válida y el parser estándar no cubre.
  2. `parseRuffOutput`/`parseShellcheckOutput` (`cli/src/commands/sensors/formatters/{ruff,shellcheck}.ts`) declaraban un tipo TypeScript (`RuffMessage[]`/`ShellcheckMessage[]`) sobre el resultado de `JSON.parse(raw)` y accedían a sus campos directamente — el tipo es una promesa que el compilador no puede verificar en runtime: `JSON.parse('{}')`, `'null'`, `'42'` o un elemento `null` dentro del array son JSON *válido* que no calza esa forma, y crasheaban el sensor run completo (no solo ese sensor) con una excepción no capturada. El fix: `Array.isArray(parsed)` + guardas de forma por elemento (`typeof`, presencia de campos) ANTES de leer cualquier propiedad, degradando a `[]`/skip en vez de crashear.
  3. `yamlString()` (`cli/src/core/renderers/cursor-mdc.ts`) asumía que `JSON.stringify` escapa "control bytes" en general y confiaba en esa premisa para producir un YAML double-quoted scalar seguro — pero `JSON.stringify` solo escapa 0x00-0x1F con secuencias `\u`; **0x7F (DEL) no está en el conjunto de caracteres que JSON exige escapar**, así que un byte DEL embebido en una descripción sobrevivía sin escapar dentro de la scalar citada, violando el propio c-printable de YAML 1.2. Esta vez el mecanismo SÍ era stdlib (no una regex hand-rolled) — la lección es la misma igual: la cobertura de un mecanismo estándar sobre un rango completo no se asume, se verifica contra el rango real que hace falta cubrir, incluso cuando "obviamente" un stdlib bien conocido ya lo resuelve.

  La contramedida no es "revisar mejor a mano" (ya se intentó las cuatro veces, en cuatro releases distintos) — es preferir una implementación ya verificada contra la especificación completa cuando existe (URLs → `URL` estándar), y cuando no existe (una forma de JSON externo específica de una herramienta, o el rango exacto de bytes que un stdlib cubre), validar la forma/cobertura en runtime o empíricamente antes de documentarla como garantía. Un tipo TS sobre `JSON.parse()`, o un comentario que afirma "X ya escapa Y", nunca son una garantía por sí solos — son una nota para el autor.

- **defensive-guard-consistency:** cuando se agrega una guarda defensiva (`?? {}`, chequeo de null, un caso "N/A" tratado como satisfecho, etc.) para blindar contra una forma de input inválida o un caso estructuralmente inaplicable, buscar TODAS las funciones/cómputos hermanos que leen el mismo campo o comparten la misma condición y aplicar la misma guarda ahí también — no solo en la función que se está editando activamente. Confirmado 2 veces: (1) `checkManifest` (`preflight/checks.ts`) ya toleraba `manifest.sensors ?? {}`, pero `computeSensorStatus`/`runSensors` — hermanas leyendo el mismo campo — no recibieron la guarda y crasheaban con `sensors: null`, tumbando `awm sensors status`/`run`/`preflight`; lo encontró el lens de robustez de `post-implementation-qa` comparando contra el árbol completo, no el reviewer de la tarea original (que solo miraba su propio diff). (2) `gatherMachine` (`diagnostics/context.ts`) computaba `devCore.present` como permanentemente `false` para cualquier agente sin directorio global de skills (hoy: Copilot) — `stepDevCore` entonces SIEMPRE intentaba un install global condenado a tirar, con rollback completo de la transaccion de `awm init`. El fix inicial solo corrigió `devCore`; un spec-review posterior encontró que `ambient` (mismo `gatherMachine`, misma condición `skillsDir === null`, unas líneas más abajo) tenía el MISMO bug sin corregir — `stepAmbient` tiraba el mismo error si `~/.awm/config.json` declaraba algún bundle `ambient`. **Grep de verificación tras un fix de este tipo:** buscar todas las ocurrencias del campo/condición guardada (`grep -rn "\.sensors\b" cli/src` / `grep -rn "skillsDir\|skill\.global" cli/src/core/diagnostics cli/src/core/init`) y confirmar que cada cómputo relacionado tiene la misma guarda — no asumir que arreglar un call site cubre a sus hermanos, y hacer el grep exhaustivo ANTES de dar el fix por cerrado, no confiar en que un reviewer posterior lo encuentre.

- **best-effort-catch-comment:** un bloque `catch {}` vacío es indistinguible de un olvido. Cuando el catch es deliberado (fallback silencioso, best-effort), agregar un comentario que explique el tradeoff: `// best-effort: <qué hace el fallback>; <qué se pierde respecto al happy path>`. Hace la intención explícita para reviewers y previene que refactors futuros añadan un re-throw "para limpieza" que rompa el comportamiento.

- **gate-order-annotation:** cuando el orden de ejecución de un bloque está dictado por una regla de CONSTITUTION (p.ej. "gates de contrato antes de early-exits"), agregar un comentario inline que la cite: `// CONSTITUTION: gates de contrato antes de early-exits`. Hace visible *por qué* el orden importa, previene reordenamientos accidentales en refactors futuros, y permite a reviewers verificar cumplimiento sin buscar la regla. El comentario va inmediatamente antes del primer gate del bloque. Confirmado necesario en más de un release: una regresión por early-exit antes del gate de pins, y otro caso con el gate `minCliVersion` colocado explícitamente antes del early-exit de extensions vacías.

## Patrones de documentación

- **verify-cmd-source-before-documenting:** cuando se documenta un comando AWM (storage target, keywords aceptados, flags), verificar `cli/src/commands/<cmd>.ts` antes de escribir. La narrativa puede sobrevivir spec-review y code-quality-review sin que nadie cheque el código fuente. En una revisión de documentación de comandos, `awm pin` fue documentado con keyword incorrecto (`base` vs `baseline`) y storage location incorrecta (`profile.json` vs `~/.awm/preferences.json`); ambos pasaron las dos primeras rondas de review.

- **runbook-as-script:** para workstreams que combinan documentación + verificación manual, escribir el doc como hipótesis y ejecutarlo literalmente como test. Las divergencias se corrigen en el doc (no en el tool); el entregable es un doc verificado contra realidad. Confirmado varias veces en la misma revisión (mensajes de error, mecánica de pin, secuencia de onboarding — todas corregidas contra el binario real durante la verificación): escribir ejemplos de output de CLI sin verificar contra el binario real es la fuente de error más común en documentación de comandos.

## Release / publish

- **El release del CLI es automático en `main` — no hay paso manual de `npm publish`.** `.github/workflows/release.yml` (trigger `push` a `main`) buildea `cli/` y corre `cli/src/release/index.js`: bump por conventional commits + `npm publish` vía OIDC Trusted Publisher + commit de bump con `[skip ci]`. **Antes de decir "publicá a mano" o de proponer/crear un workflow de release paralelo, verificá que `release.yml` ya lo cubre** — ya existe y es completo. El nivel de versión sale del prefijo de conventional commit del merge; regla no-negociable en `CONSTITUTION.md` → "Release del CLI".

## Auto-verificación del CLI (dogfooding)

- **`awm` en el PATH puede ser una instalación global publicada, desconectada del working tree que estás editando.** Al desarrollar este mismo CLI, el binario que resuelve `which awm` suele venir de una instalación global de npm (`npm i -g agentic-workflow-manager`) con una versión publicada anterior — no del código que acabás de cambiar en `cli/src/`. Correr `awm sensors run` "en carne propia" contra ese binario prueba una versión vieja, no tu diff: un bug ya arreglado localmente (ej. exit 127 clasificado como `fail`) puede seguir viéndose roto (`skipped`) porque el binario global nunca se actualizó. Confirmado comparando la salida de `awm sensors run` (global) contra `node dist/src/index.js sensors run` (build local): resultados distintos para el mismo sensor. **Al auto-verificar este CLI durante su propio desarrollo, siempre `npm run build && node dist/src/index.js <comando>` desde `cli/` — nunca confiar en `awm` bare del PATH.**

## Subagentes concurrentes y git

- **Nunca despachar subagentes con acceso a Bash en paralelo sobre el mismo working tree si alguno puede correr `git checkout <ref> -- <path>` (u otro comando que mute el índice/working tree) para "mirar una versión vieja".** Caso confirmado: varios subagentes de QA corrieron en paralelo sobre el mismo checkout; uno de ellos ejecutó `git checkout <commit-base> -- .` para comparar sensores contra una baseline preexistente, y su restore posterior quedó incompleto — probablemente por carrera con los `git diff`/`git show` de sus hermanos concurrentes tocando el mismo working tree al mismo tiempo. El resultado: varios archivos revertidos a una versión anterior a tareas ya completadas, silencioso hasta que un `git status` de rutina lo mostró. El historial de commits (HEAD, reflog) nunca se corrompió — el daño fue puramente de working tree + índice, y `git checkout HEAD -- .` lo revirtió limpio una vez detectado.
  - **Para inspeccionar contenido histórico de un archivo sin tocar el working tree, usar `git show <ref>:<path>` (lee, no muta) en vez de `git checkout <ref> -- <path>` (muta índice y working tree).** Es la causa raíz evitable: `git show` responde la misma pregunta ("¿qué decía este archivo en tal commit?") sin ningún riesgo de dejar el árbol en un estado intermedio si el proceso se interrumpe o compite con otro.
  - **Si un subagente necesita comparar "antes vs. después" de forma más elaborada que un diff (ej. correr el binario contra ambas versiones), aislarlo en un worktree separado (`git worktree add`), nunca mutar el checkout compartido.**
  - **El controlador debe verificar `git status --short` después de cualquier ronda de subagentes paralelos con acceso a Bash, antes de confiar en sus reportes** — no asumir que "reportó DONE" implica que el working tree está en el estado esperado. Este chequeo fue lo único que detectó la corrupción en el caso de arriba; nada en los reportes de los subagentes involucrados la mencionaba.
  - **`git commit --amend --reset-author` (el remedio que sugiere el stop-hook de firma cuando detecta commits sin firmar) resetea el `AuthorDate` Y el `CommitDate` al momento del amend — no solo la identidad.** Un `git rebase --exec "git commit --amend --no-edit --reset-author"` sobre varios commits sin firmar (para resolver la advertencia del hook) colapsó sus timestamps reales (minutos de trabajo real de subagentes distintos) a segundos de diferencia entre sí — el momento en que corrió el propio rebase, no el momento original de cada commit. Un lens de QA posterior, razonando sobre esos timestamps ya corrompidos, concluyó erróneamente que pasos de verificación que tardan tiempo real (sleeps de sonda, ciclos RED/GREEN) nunca pudieron haber ocurrido — falso positivo con causa raíz identificable, no evidencia real de trabajo no hecho. **Si el timing real de los commits importa para auditoría/forense futura, o si una QA de esta rama va a correr después de un rebase de firma, revisar el `AuthorDate` real (`git log --format='%ad' --date=iso-strict`) antes de tomar timestamps como prueba de cuándo ocurrió el trabajo — y, si es evitable, considerar firmar en el momento del commit original en vez de corregir con un rebase masivo después.**

## Ledger y trazabilidad

- **`awm ledger add` puede correr dos veces para el mismo hallazgo — el controlador debe leer `awm ledger list` completo, no confiar en el conteo de `awm ledger recurring` a ciegas.** Confirmado ≥4 veces en un solo release: entradas con `phase`+`signature`+`desc` byte-idénticos y timestamps a milisegundos de diferencia, más entradas de prueba sueltas que algún subagente dejó al verificar que `awm` respondía antes de loguear el hallazgo real. El riesgo: `awm ledger recurring --min 2` cuenta duplicados exactos como si fueran 2 ocurrencias reales, lo que puede empujar de forma espuria un hallazgo trivial a la categoría "sistémico" en el triage de `harness-retro` modo desatendido. Mitigación: reconciliar contra `awm ledger list` (contenido real) en cada paso, no contra el resumen en prosa de cada subagente — mismo principio que "el controlador debe verificar `git status --short`" arriba, aplicado al ledger en vez del working tree.

- **Depurar directamente contra evidencia real (logs de CI, stack traces) sin invocar formalmente el skill `systematic-debugging` deja el ledger vacío incluso cuando hay hallazgos reales — y un ledger vacío con hallazgos reales es en sí mismo el hallazgo de retro** (ver "Empty-ledger consistency check" del skill `harness-retro`). Caso confirmado: un ciclo completo de varias rondas de fixes contra CI real de `windows-latest` (~137 fallos → 0, incluida una reversión arquitectónica documentada en el propio código fuente) produjo **cero** entradas en el ledger, porque el trabajo se hizo leyendo logs de CI y parcheando directamente, no a través de una invocación explícita de `systematic-debugging` (que es quien emite `awm ledger add --phase debugging` al confirmar una causa raíz). `harness-retro` detectó el vacío contra la evidencia de la sesión y tuvo que reconstruir el registro post-hoc. Regla: al confirmar una causa raíz mientras se depura directamente contra evidencia (sin pasar por el skill), emitir el `awm ledger add --phase debugging --polarity finding ...` de todos modos — el skill formaliza el paso, pero la obligación de loguear no depende de invocarlo.

## Layout del repo y de la instalación

- **Este repo** contiene solo el CLI TypeScript (`cli/`). El contenido (skills, bundles, sensor-packs, hooks) vive en repos externos: `awm-baseline-registry` y `awm-documentation-registry`.
- **No hay `registry/` en este repo** ni `~/.awm/cli-source/`. El concepto `cli-source` fue eliminado.
- **Layout de instalación:** `~/.awm/registries/<name>/` — cada registry configurado se clona aquí (ej. `~/.awm/registries/baseline/`). Los skills se instalan como symlinks hacia esos paths.
- **Descubrimiento de contenido:** `contentRoots()` devuelve los paths bajo `~/.awm/registries/` según la config. No hay constante fija de `baseRoot` ni de `cliSource`.
